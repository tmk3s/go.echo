# マルチエージェント・コードレビュー

対象コードを **専門サブエージェントに並列で投げ**、返ってきた結果を **あなた（スキル側）が統合して** ユーザーに 1 本のレポートとして返します。

## ステップ 1: レビュー対象を決める

引数 `$ARGUMENTS` から **モード** と **対象ファイル一覧** を決める。

### A. 差分モード（変更点だけを見る）

| 引数 | 対象 | 取得コマンド |
|---|---|---|
| なし | 未コミット差分（無ければ main との差分） | `git diff HEAD` → 空なら `git diff main...HEAD` |
| `staged` | ステージ済み | `git diff --staged` |
| ブランチ名 | main との差分 | `git diff main...<branch>` |
| `#123` / 数字 | PR | `gh pr diff 123` |

変更ファイル一覧と差分量を確認する:

```bash
git diff HEAD --stat
```

**差分が空なら、ここで止まってユーザーにその旨を伝える。** サブエージェントは起動しない。
その際、「既存コード全体を見るなら `/review all` や `/review <パス>` が使えます」と案内する。

### B. 全体モード（既存コードそのものを見る）

| 引数 | 対象 |
|---|---|
| `all` | `app/` 配下すべて（フロント含む） |
| パス（`app/usecase` など） | そのパス配下のファイル全体 ※差分ではない |

対象ファイル一覧は git 管理下のものだけを拾う:

```bash
git ls-files 'app/usecase/*' | grep -vE '_test\.go$'   # 例
```

除外するもの: `node_modules`、`.next`、`app/tmp`、生成物、`vendor`。
テストファイルは既定では除外するが、**テストの有無自体を指摘対象にする**ためファイル名は一覧として把握しておく。

**ファイル数が多すぎる場合の扱い**:

- 対象が **40 ファイルを超える** 場合は、そのまま投げずにユーザーに確認する。
  「対象が N ファイルあります。このまま全部見ますか？ それとも範囲を絞りますか？（例: `app/usecase` だけ）」
- ユーザーが続行を選んだら、エージェントごとの担当ファイルを **1 エージェントあたり 25 ファイル程度** に収まるよう分割し、同じエージェントを複数インスタンス並列で起動する（`label` で区別する）。

## ステップ 2: 起動するサブエージェントを選ぶ

対象ファイルのパスで振り分ける。**該当しないエージェントは起動しない**（トークンの無駄）。

| 条件 | エージェント |
|---|---|
| `app/**/*.go` が対象に含まれる | `go-backend-reviewer` |
| `app/frontend/**` が対象に含まれる | `frontend-reviewer` |
| 常に（対象が 1 ファイルでもある限り） | `security-reviewer` |

## ステップ 3: サブエージェントを並列起動する

**選んだエージェントの `Agent` 呼び出しを、必ず 1 つのメッセージにまとめて発行する**（そうしないと直列実行になり待ち時間が倍増する）。
結果を待って統合する必要があるため、**`run_in_background: false`** を指定する。

各エージェントへのプロンプトには以下を必ず含める:

1. **モードの明示**（「差分レビュー」か「ファイル全体のレビュー」か）
2. 対象の取得方法、または対象ファイルの一覧（ステップ 1 で得たパス）
3. 「自分の担当領域外のファイルは無視すること」
4. 「最終メッセージは、エージェント定義の出力フォーマットの Markdown のみを返すこと」

### 差分モードの呼び出し例

```
Agent(
  subagent_type: "go-backend-reviewer",
  description: "Go差分レビュー",
  run_in_background: false,
  prompt: "【差分レビュー】未コミットの差分をレビューしてください。差分は `git diff HEAD` で取得できます。\n
           変更された Go ファイル:\n  - app/usecase/employee_usecase.go\n  - app/infrastructure/repository/employee_repository.go\n
           担当領域外のファイルは無視してください。\n
           最終メッセージはエージェント定義の出力フォーマットの Markdown のみを返してください。"
)
```

### 全体モードの呼び出し例

```
Agent(
  subagent_type: "go-backend-reviewer",
  description: "usecase層レビュー",
  run_in_background: false,
  prompt: "【ファイル全体のレビュー】以下のファイルを最初から最後まで読み、現状のコードをレビューしてください。差分ではありません。\n
           対象ファイル:\n  - app/usecase/employee_usecase.go\n  - app/usecase/employee_usecase_import.go\n  - app/usecase/company_usecase.go\n
           担当領域外のファイルは無視してください。呼び出し元・呼び出し先は必要に応じて参照して構いませんが、指摘は対象ファイルに限定してください。\n
           全体モードでは、個々の行の指摘に加えて『設計上の一貫性の崩れ』『レイヤー責務のずれ』『重複している処理』も 1〜3 件挙げてください。\n
           最終メッセージはエージェント定義の出力フォーマットの Markdown のみを返してください。"
)
```

## ステップ 4: 結果を統合する

サブエージェントの出力は **ユーザーには見えない**。必ずあなたが内容を読んで再構成する。そのまま貼り付けるのではなく、以下を行う:

1. **重複の統合**: 同じ箇所への複数エージェントからの指摘は 1 件にまとめ、どのエージェントが挙げたかを併記する。
2. **矛盾の裁定**: 指摘が食い違う場合は、あなた自身が該当ファイルを `Read` して確認し、どちらが正しいか判断して書く。**サブエージェントの結論を鵜呑みにしない。**
3. **明らかな誤検出の除外**: 確認して事実と異なる指摘は落とす。落とした場合はレポート末尾に 1 行で理由を書く。
4. **並び替え**: severity（high → low）、同 severity 内では confidence が高い順。
5. **全体モードのみ**: 複数エージェントが別々に挙げた設計観点の指摘を束ね、「設計・構造」セクションとして 1 箇所にまとめる。

## ステップ 5: レポートを出力する

以下の形式でユーザーに返す。ファイルには書き出さず、会話に直接出力する。

```markdown
# レビュー結果

**モード**: 差分レビュー ／ 全体レビュー
**対象**: <対象の説明>（N ファイル）
**実行エージェント**: go-backend-reviewer, security-reviewer

## サマリ
<2〜3文。差分モードならマージして良い状態かを最初に書く。全体モードなら
 コードベースの健全性と、最初に手を付けるべき箇所を書く>

## 要対応（high）
### 1. `パス:行` — 一文での指摘 <!-- by: go-backend-reviewer -->
**問題**: …
**修正案**:
（具体的なコード片）

## 検討推奨（medium / low）
- `パス:行` — 指摘（by: …）: 一文での説明と修正方針

## 設計・構造（全体モードのみ）
- <レイヤー責務のずれ、重複、一貫性の崩れ。ファイル横断の観点>

## 良かった点
- …

## 補足
- 確認できなかった範囲 / 除外した指摘とその理由
```

指摘が 1 件も無い場合は、セクションを並べずに「サマリ」＋「良かった点」だけを簡潔に返す。

## 注意

- **サブエージェントを 1 つも起動せずにこのスキルを完了してはいけない**（対象が空の場合を除く）。
- 同じエージェントを同じ対象で二重に起動しない（全体モードでのファイル分割は例外）。
- レビューは指摘までが仕事。**勝手にコードを修正しない。** 修正まで求められたら、レポート提示後にユーザーに確認する。
